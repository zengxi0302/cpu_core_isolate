# CPU 核心故障自隔离 — 业务例会汇报材料

> 适用场景：业务例会、产品评审、管理层汇报
> 重点：业务价值、客户痛点、ROI

---

## Slide 1: 一句话价值

> **把 "整机宕机丢100个VM" 变成 "隔离一个核丢1个VM"**

- 故障影响面缩小 **100 倍**
- 单节点可用性从 3 个 9 提升到 **5 个 9** 级别
- 客户感知从 "大规模事故" 变成 "单 VM 偶发重启"

## Slide 2: 业务背景

### 客户痛点

公有云计算节点（宿主机）典型配置：128 核 CPU，运行 50-100+ VM

**当前**：CPU 硬件偶发故障 → 整机宕机重启 → **全部 VM 被杀**

```
影响链路:
  CPU Cache 1bit 翻转 → 内核 panic → 整机重启
  → 50+ VM 同时丢失 → 客户大量投诉 → SLA 赔付
```

**真实场景**：
- Intel/AMD 服务器年故障率 ~0.5-2%（per server）
- 单次事件影响：50+ 客户同时受损
- 修复时间：5-10 分钟（重启 + VM 恢复调度）

## Slide MFI-1: 新战场——内存故障（对应 PPT 第 8 页）

### 为什么扩展到内存

内存（DRAM）与 CPU 同为易损器件，UCE 同样经 MCE 上报，是宿主机宕机的另一大来源。

**现有能力边界**：

| 故障场景 | 现有行为 | 结果 |
|---------|---------|------|
| 用户态进程消费毒页 | memory_failure 杀进程 | ✓ 单 VM 损失 |
| copy_from_user 等路径 | extable fixup 杀进程 | ✓ 单 VM 损失 |
| **内核态消费毒页（无 fixup）** | mce_panic() | ✗ **整机宕机** |
| 巡检发现 UCE（未消费） | 依赖发行版配置 | △ 机会被浪费 |
| CE 高频页（UCE 前兆） | 仅 EDAC 计数 | △ 坐等恶化 |

**关键洞察**：内核态 UCE 可恢复性取决于「落点 × 消费方式」（A–E 五类，
详见 memory-fault-isolation-design.md §1.2）。宿主机内存大头是虚机页，
多数内核态 UCE 落点可救。

---

## Slide MFI-2: 内存故障域（MFI）三层防线（对应 PPT 第 9 页）

同一个 cpu_fault_isolate.ko，复用 CFI 的 panic 抑制 / netlink / sysfs 底座：

1. **事前 · CE 预隔离**：页级滑动窗口计数，达阈值 soft offline（先迁移再下线）→ 业务零感知
2. **事中 · 异步 UCE 兜底**：patrol scrub/SRAO 数据未被消费 → 页隔离替代 panic
3. **事后 · 内核态落点甄别**：用户/虚机页 → 杀属主+隔离页；内核页 → 受控 panic + kdump

**诚实的边界**：内核自身数据被同步消费（场景 E）没有隔离机会，硬扛=静默
数据损坏。策略是受控 kdump 保现场 + 预隔离压低发生概率。

## Slide MFI-3: 内存域业务价值（对应 PPT 第 23 页）

| 故障场景 | 无 MFI（现状） | 启用 MFI |
|---------|--------------|---------|
| CE 高频页（UCE 前兆） | 坐等恶化为 UCE | 提前迁移页内容，零损失 |
| patrol scrub 发现 UCE | 依赖配置，可能整机宕机 | 页隔离，不宕机 |
| 内核态消费 UCE（虚机页） | 整机宕机，60 台全丢 | 杀 1 台 VM，59 台无感 |
| 内核自身数据消费 UCE | 整机宕机（或静默损坏） | 受控 kdump，保留现场 |
| DIMM 介质持续劣化 | 反复报错直至故障 | 越限上报，建议疏散+报修 |

## Slide B7 (新增): VM 处置策略升级——不再默认杀

CPU 不再下线 → vCPU 进程是否被影响**完全取决于 affinity 配置**。原项目"统一杀 VM"过激；改成**三级分级响应**：

| Case | host 上 vCPU affinity | inactive 后调度行为 | guest 内感知 | daemon 动作 |
|------|---|---|---|---|
| A | 不绑核（默认）| 自然漂到健康核 | **无** | 不动 |
| B | **绑死故障核** | 仍在故障核跑 | 无感但**故障 cache 在用** | **必须改 vcpupin** |
| C | 绑核组（含故障核）| 漂到组内健康核 | 无 | 可选预扩 |

**三级响应**（按代价递增）：

```
Level 1 (首选, 毫秒级, 0 感知):  virsh vcpupin <dom> <vcpu> 健康核列表
Level 2 (次选, 秒级, 短暂感知): virsh migrate --live → 其他节点
Level 3 (兜底, 秒级, guest 中断): virsh destroy
```

**业务影响**：原 100% 杀 VM → 实测仅 **<10%** 走 L2/L3（NUMA 强约束场景）；90%+ VM **L1 即解**，客户**毫无感知**。

## Slide B8 (新增): 物理机里程碑达成

### 实测数据

| 跑次 | 环境 | 模式 | 结果 | 关键证据 |
|---|---|---|---|---|
| #1 | HCE2 物理机 (5.10.0-182.r3353_271_366) | inactive | **22 PASS / 0 FAIL** | cpu35 隔离 **437 IRQs 迁移**, 0.3ms 完成 |
| #2 | 同上 + hw mode | inactive | **22 PASS / 0 FAIL** | hw probe 准确识别物理机限制 |
| #3 | 同上 | soft | **22 PASS / 0 FAIL** | 兜底模式同样通 |
| 累计 | VM × 3 + 物理机 × 3 | full / inactive / soft | **128 PASS / 0 FAIL** | 跨内核流跨模式无失败 |

### dmesg 里物理机才看得到的硬证据

```
EDAC MC2: 0 CE memory read error on
  CPU_SrcID#1_MC#0_Chan#2_DIMM#0
  channel:2 slot:0 page:0x40d4833 ... Row:0x160 Column:0x608

cpu_fault_isolate: cpu35: inactive-isolated
  (cleared from cpu_active_mask + migrated 437 IRQs;
   CPU stays online)
```

EDAC skx 真实解码到 DIMM channel/slot/row/col 级别——这条信息是 VM 永远看不到的，**对后续"具体哪根内存条要换"必备**。

### 历史曲线

| 阶段 | 物理机现象 | 解法 |
|---|---|---|
| 第 1 次 cfi 调 cpu_device_down | ABBA 死锁雪崩 | 加 cascade 防护 |
| 第 2 次 还在死锁 | pid7+pid554 ABBA 锁死 | 加软隔离 soft |
| 第 3 次 livepatch 完整下线 | percpu_counter hardlockup | 不走完整 down |
| **第 4 次 inactive 模式** | **0.3ms 完成 / 0 死锁** | **本方案** |
