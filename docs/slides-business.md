# CPU 核心故障自隔离 — 业务例会汇报材料

> 适用场景：业务例会、产品评审、管理层汇报
> 重点：业务价值、客户痛点、ROI

---

## Slide 1: 一句话价值

> **把 "整机宕机丢100个VM" 变成 "隔离一个核丢1个VM"**

- 故障影响面缩小 **100 倍**
- 单节点可用性从 3 个 9 提升到 **5 个 9** 级别
- 客户感知从 "大规模事故" 变成 "单 VM 偶发重启"

---

## Slide 2: 业务背景

### 客户痛点

公有云计算节点（宿主机）典型配置：128 核 CPU，运行 50-100+ VM

**当前**：CPU 硬件偶发故障 → 整机宕机重启 → **全部 VM 被杀**

```
影响链路:
  CPU Cache 1bit 翻转 → 内核 panic → 整机重启
  → 50+ VM 同时丢失 → 客户大量投诉 → SLA 赔付
```

**真实场景**：
- Intel/AMD 服务器年故障率 ~0.5-2%（per server）
- 单次事件影响：50+ 客户同时受损
- 修复时间：5-10 分钟（重启 + VM 恢复调度）

## Slide 5: 技术方案概要（非技术人员版）

```
┌─────────────────────────────────────────────────┐
│  正常运行                                        │
│  CPU1 CPU2 CPU3 ... CPU128                       │
│  [VM] [VM] [VM] ... [VM]                        │
└─────────────────────────────────────────────────┘
              │
              │  CPU3 发生硬件故障
              v
┌─────────────────────────────────────────────────┐
│  故障检测 → 自动隔离 → 上报                      │
│  CPU1 CPU2 [XX] ... CPU128                       │
│  [VM] [VM] [💀] ... [VM]                         │
│            ↑                                     │
│       仅此 VM 丢失                                │
│       其余 VM 完全不受影响                        │
└─────────────────────────────────────────────────┘
              │
              v
┌─────────────────────────────────────────────────┐
│  上层调度：将丢失的 VM 迁移到其他节点重建         │
│  节点标记为 "降级"，后续不再调度新 VM 到此节点    │
└─────────────────────────────────────────────────┘
```

## Slide 10: 风险与应对

| 风险 | 概率 | 应对 |
|------|:---:|------|
| kprobe 在生产内核被禁用 | 低 | 可提供 1 行内核 patch 作为备选 |
| tolerant=3 理论上降低保护 | — | CFI 主动处理所有 fatal MCE，反而更精准 |
| 故障 CPU 上的 VM 数据损坏 | 必然 | 属于 "止损"，与 panic 相比从 N 个 VM 降到 1 个 |
| 模块本身 bug 导致误隔离 | 低 | user_pinned 人工锁定 + auto_isolate 开关 |
