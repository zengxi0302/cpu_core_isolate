## 一、问题（Problem）

公有云计算节点（宿主机）上单台物理机往往承载上百个虚拟机（VM）。当 CPU
缓存、TLB、总线等核心器件，或内存（DRAM/HBM）器件出现不可纠正硬件错误
（UCE）时，Linux 内核在机器检查异常处理流程 `do_machine_check()` 的早期就会
调用 `mce_panic()` 触发整机宕机（panic + kdump + 重启）。其后果是：**单个
器件的局部故障，牵连同一台宿主机上全部 VM 一起掉线**，故障爆炸半径被放大到
整机。同时，故障事件在 panic 时刻根本来不及流入内核可处置的解码链（decode
chain），系统失去了"局部隔离、整体存活"的全部机会。

而云厂商面对的现实约束是：机型异构（Intel/AMD x86 与鲲鹏 arm64 并存）、内核
碎片化（upstream 与各厂商 vendor 内核如 HCE2/HCE3 并存，部分内核关键符号
未导出、无 sysfs、且 CPU 热插拔回调链存在死锁缺陷），**不可能为每个内核版本
逐一修改并重新发布内核源码**。因此需要一种以可热插拔、可灰度、可回滚的外挂
内核模块形态交付，且能同时覆盖 CPU 与内存两大故障域、跨架构自适应的硬件故障
运行时自隔离方案。

## 二、现有技术与GAP（Existing Technology / GAP）

业界与既有专利已有两类相关思路，但均不能覆盖上述完整需求：

其一，以 **US 11829265、US 11385974** 为代表的"虚拟机宿主机内存不可纠正错误
恢复"方案，由**内嵌于宿主机内核**的机器检查处理程序识别"内核访问 guest
内存"产生的 UCE，转而通知虚拟机管理器向受影响 VM 注入模拟 MCE 或迁移该 VM，
以替代 panic。其局限在于：仅覆盖**内存**错误而不处理 CPU 缓存/核心故障；恢复
逻辑是**内核源码的组成部分**，须定制并随内核版本维护，无法以外挂模块在既有
内核上即插即用；且不涉及物理 CPU 核心的隔离。

其二，以 **US 12222830、US 11847036、US 11531607** 为代表的"失效从核 CPU
故障隔离与恢复"方案，面向**裸金属非对称多处理（AMP）**场景，由 NMI 处理程序
触发自定义 panic 处理并**关停 CPU 核**、再将上下文切回主实例恢复。其局限在
于：面向裸机 AMP 而非云虚拟化宿主机；依赖真实**关核**与上下文切换，而非
"保持物理在线但对调度与中断不可见"；不区分缓存层级，也不含面向 VM 的优雅
疏散协同。

此外，Linux 内核自带的纠错隔离原语（`mce_tolerant` 旋钮、`CONFIG_RAS_CEC`、
`memory_failure()`、`soft_offline_page()`、CPU 热插拔、`isolcpus`）均为
**孤立单点能力**：`isolcpus` 仅启动期静态生效，无法对运行中突发故障的核动态
隔离；CEC 仅限 x86、策略固定、无上报；热插拔下线在 vendor 内核存在硬死锁。

**GAP 在于**：现有技术中没有一种"以不改内核源码的可加载模块，在运行时抑制
本不该发生的整机 panic、接管故障事件、按缓存物理拓扑分级隔离 CPU 核心、以无
下电方式绕开热插拔死锁、并以白名单落点甄别守住静默数据损坏边界、同时统一覆盖
CPU 与内存故障域并跨架构自适应"的端到端编排方案。

## 三、创新点（Innovation Points）

本发明提供一种面向云宿主机的、以可加载内核模块（不修改内核源码）形态交付的
CPU/内存硬件故障运行时自隔离方法与系统，其核心是把"单器件故障→整机宕机"
重构为"单核/单页/单 VM 损失"的可控降级。整体方案由以下相互配合的机制有机
组成：

**（1）运行时 panic 抑制与故障接管接力。** 模块在加载阶段通过 kprobe 定位
内核中未导出的 `mce_tolerant` 符号并直接写入容忍级，使 `do_machine_check()`
中所有受容忍级门控的 panic 分支（多核同步超时、MCIP 未置位、致命错误等）退化
为"记录并返回"，故障事件因此回流至机器检查解码链；模块注册的解码链通知器随即
对事件分类并派发隔离动作，形成"拦截 panic→接管事件→执行隔离"的闭环；同时
注册 panic 通知器作为第二层兜底取证，并在卸载时完整回滚全部被修改的内核状态。

**（2）三档自适应隔离引擎与无下电隔离模式。** 针对部分 vendor 内核热插拔
下线会触发硬死锁（如 `percpu_counter_cpu_dead`）而使"隔离"恶化为"二次
宕机"的问题，提出 full（真实下线）/ **inactive（无下电隔离，默认）** / soft
三档，按内核能力自适应选择。其中无下电隔离模式对故障核从调度器活动掩码
（`cpu_active_mask`）清位、并将该核全部可迁移中断迁出至健康核，**完全不调用
热插拔下线接口**，使 CPU 保持物理在线但对调度器与中断子系统"形同下线"，从而
绕开整条热插拔死锁面。配套"跨核隔离调度"——因故障核可能无法执行自身工作
队列，隔离动作被派发到健康核执行——以及"保护 0 号核、拒绝自隔离、拒绝下线
最后一个核"等安全约束。

**（3）按缓存物理拓扑分级的隔离决策。** 在错误解码后按"缓存层级×共享域"
分流：L1/L2/TLB/总线等 per-core 故障→隔离上报该核；而 L3/LLC 为 socket
共享，隔离单核不解决根因反而误伤健康核，故仅记账并经 netlink 上报、由用户态
决策（地址级页隔离或 socket 级疏散），并修正"内存错误码误计入 CPU 计数而
拖垮健康核"的跨域缺陷。

**（4）内核-用户态协同的延迟隔离协议。** 通过通用 netlink 定义双向协议与
延迟隔离状态机：内核进入隔离态即通知守护进程，由其热迁移/疏散该核 VM 后回送
确认，内核据此执行下线；若在超时窗口内未收到确认则强制下线兜底，从而在"尽快
隔离"与"VM 零损失优雅疏散"之间取得有界折衷。

**（5）内核态 UCE 落点甄别白名单（panic 抑制的安全阀）。** 鉴于 panic 抑制
对"内核自身数据被同步消费且无异常修复表项"的致命错误会带来比宕机更糟的静默
数据损坏风险，本发明以"故障页归属（用户/虚机页 vs 内核页）×消费方式（异步
未消费/有修复表项/无修复表项）×可恢复信号（返回地址有效位、单 bank、无处理器
上下文损坏标志）"进行二维判决：异步未消费走零损失页隔离，有修复表项交内核
自恢复，无修复表项但毒页为用户/虚机页且可恢复信号成立则定点终止属主进程
（属于 VM 则上报异地重建）；**凡不在白名单内一律主动快速 panic 并触发 kdump
取证，绝不静默继续**。甄别全程只读页元数据、不触碰毒页本身。

**（6）统一双故障域与跨架构框架。** CPU 故障域与内存故障域共用同一套 panic
抑制层、netlink、守护进程协议与 sysfs；内存域额外提供页级 CE 前兆预隔离（达
阈值即无损迁移下线，业务无感）与 DIMM/rank 介质级记账（达阈值建议整机疏散
报修）。整体采用"公共策略层＋可插拔架构后端（x86 MCE/MCACOD 与厂商 FMA 钩子、
arm64 GHES/APEI/CPER）＋运行时符号与钩子探测"的分层结构，使同一份模块在
Intel/AMD/鲲鹏及 upstream 与 vendor 内核上自适应运行，并与
rasdaemon/EDAC/mcelog/CEC 共存不冲突。

## 四、技术效果与业务价值（Technical Effect / Business Value）

在 Huawei 2288H V5 + HCE2 真实物理机上以**完全相同的故障注入**完成对照实证：
未加载本模块时内核 `mce_panic` 触发 kdump、整机重启；加载本模块（无下电隔离
模式）时同一事件被接管，故障核被无下电隔离（一次性迁出 462 个中断、CPU 仍在
线），**整机存活**，且 `taskset` 绑核失败、该核负载趋零，证明故障核对业务真正
不可见、又未触发热插拔死锁。

由此带来的技术效果与业务价值是：将宿主机硬件故障的爆炸半径从"整机上百个 VM
全部掉线"收敛为"仅故障核绑定的单个 VM 受影响、甚至经热迁移零损失"；以纯外挂
模块交付，跨内核版本零源码改动、可灰度、可热插拔、可回滚，大幅降低云厂商上线
与长期维护成本；隔离决策与物理故障域精确对齐，最大化健康算力留存；内存侧把
故障处置从"被动等 UCE 宕机"前移到"CE 前兆期零损失预隔离"并打通介质换件闭环；
落点甄别白名单则在扩大可恢复覆盖面的同时杜绝静默数据损坏，使 panic 抑制成为
生产可用的安全方案。一套框架统一覆盖 CPU 与内存两大宿主机宕机源、覆盖主流
异构机型，显著提升公有云的整体可用性与单机承载稳定性。

## 附：诚实的覆盖边界（写入说明书"有益效果的限定"避免过度主张）

- 内核态 **AR 严重性、无 fixup** 事件（如 LMCE + SRAR 命中内核数据）走
  `mce_panic("Fatal local machine check")` 的**无条件路径**，不受容忍级门控
  ——本方案对此**主动 kdump 兜底**而非声称可救（创新点 5 的白名单正是为此
  设边界）。
- `full` 真下线模式在未打 livepatch 的 vendor 内核会撞
  `percpu_counter_cpu_dead` 死锁，故默认用 `inactive`（创新点 2 的价值所在）。
- 说明书宜将"有益效果"限定为"消除**本不该发生**的整机 panic，并对不可恢复
  故障提供受控 kdump 取证"，而非"消除一切 panic"。
